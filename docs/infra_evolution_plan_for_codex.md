# План эволюции локальной и Kubernetes-инфраструктуры для pet project

## Цель

Зафиксировать простой и практичный путь развития инфраструктуры проекта без преждевременного усложнения.

Нужна не максимальная “правильность” с первого дня, а последовательная эволюция локальной среды
разработки и локального деплоя:

1. сначала быстрое локальное развитие через Docker Compose;
2. затем переход к локальному Kubernetes через kind и упаковке деплоя через Helm;
3. дополнительно — Minikube как отдельная песочница для изучения Kubernetes-фич, не как основной путь разработки.

---

## Общий принцип

Инфраструктура должна развиваться вместе с проектом.

На раннем этапе важнее:
- быстро поднимать стек;
- удобно дебажить сервисы;
- просто подключать PostgreSQL, Redis, Kafka и другие компоненты;
- не тратить много времени на Kubernetes-операционку.

Когда core-функциональность станет стабильной, нужно перейти к более production-like сценарию:
- локальный Kubernetes;
- шаблонизированный deploy;
- подготовка к воспроизводимой локальной automation flow;
- проверка readiness/liveness, rollout и конфигурации окружений.

Поэтому целевой путь такой:

1. **Старт:** Docker Compose  
2. **Потом:** kind + Helm  
3. **Дополнительно:** Minikube как sandbox для изучения Kubernetes-возможностей

---

# Этап 1. Старт: Docker Compose

## Зачем этот этап нужен

Docker Compose нужен как самая быстрая и понятная точка входа в проект.

На этом этапе основная задача — не учиться Kubernetes, а:
- реализовать бизнес-логику сервиса;
- собрать локальный стек зависимостей;
- наладить запуск проекта одной командой;
- обеспечить удобную отладку backend и инфраструктурных компонентов.

## Почему именно Docker Compose

Потому что на старте он дает:
- минимальную сложность;
- быстрый startup;
- понятную сетевую модель;
- простую отладку;
- удобную работу с volume, env и портами.

Docker Compose особенно хорошо подходит, пока проект активно меняется и часто ломается архитектурно.

## Что должно запускаться через Docker Compose

На первом этапе желательно поднимать:
- `postgres`
- `redis`
- `kafka` и связанные компоненты, если они уже нужны
- `clickhouse`, если аналитика уже включена
- `elasticsearch` и `kibana`, если observability уже дошла до этого уровня
- `prometheus` и `grafana`
- опционально сам `api-http-stdlib` и `worker`

При этом допустим гибридный режим:
- инфраструктура в Compose;
- `api-http-stdlib` и `worker` запускаются локально из IDE.

Это особенно удобно на ранней стадии разработки.

## Что должно быть результатом этапа

На выходе этого этапа должно быть:
- локальное окружение, поднимаемое одной командой;
- понятный `docker-compose.yml`;
- документированный запуск;
- готовые env-конфиги для dev;
- health/readiness endpoints у приложения;
- предсказуемая локальная разработка без Kubernetes.

## Ограничения этапа

Важно зафиксировать:
- Docker Compose — это **основной инструмент ранней разработки**, но не конечная модель инфраструктуры;
- он нужен для быстрого старта, а не для имитации production 1 в 1;
- не нужно пытаться решать через Compose задачи, которые естественно решаются позже через Kubernetes.

# Этап 2. Потом: kind + Helm

## Зачем нужен переход на этот этап

Когда проект уже перестанет быть просто набором локально запускаемых сервисов и появится желание:
- запускать систему в Kubernetes локально;
- приблизить dev/staging сценарий к production;
- подготовить основу для локальной automation flow;
- перейти к нормальному описанию deploy-процесса;

нужно двигаться в сторону:
- **kind** как локального Kubernetes-кластера;
- **Helm** как основного способа описания и установки приложения в локальном Kubernetes.

## Почему именно kind

`kind` нужен как легкий и практичный локальный Kubernetes:
- запускается в Docker;
- хорошо подходит для локальной разработки;
- хорошо подходит для CI;
- прост в удалении и пересоздании;
- позволяет тестировать реальные Kubernetes-манифесты и deployment flow.

Он лучше подходит как рабочая локальная база, чем более тяжелые локальные k8s-варианты.

## Почему именно Helm

Helm нужен как основной deployment-артефакт локального Kubernetes-контура проекта.

Через Helm нужно описывать:
- Deployment
- Service
- Ingress
- ConfigMap
- Secret
- values для dev/staging/prod
- параметры image/tag/resources/replicas/env

Главная идея:
- **не писать и не поддерживать большой набор raw YAML вручную**
- **не дублировать конфигурацию между окружениями**
- **иметь воспроизводимый способ установки и обновления приложения**

## Какова роль Helm в этом плане

Helm должен стать:
- стандартом упаковки приложения;
- основой для локального запуска в k8s;
- основой для воспроизводимого локального deploy;
- единым способом конфигурирования окружений.

То есть локально проект должен деплоиться одним и тем же conceptual way:
- собрали image
- передали tag
- сделали `helm upgrade --install`

## Что должно входить в Helm chart

Минимально chart должен покрывать:
- `api-http-stdlib`
- `worker`
- ingress/service
- env/config
- probes
- ресурсы контейнеров
- image repo/tag
- secrets/config values

Инфраструктурные зависимости можно развести так:
- часть оставить внешними;
- часть подключать отдельными chart’ами;
- часть временно оставить вне основного chart.

Не нужно пытаться сразу запихнуть весь мир в один chart.

## Что должно быть результатом этапа

На выходе этого этапа должно быть:
- локальный `kind`-кластер;
- Helm chart проекта;
- values для локального окружения;
- возможность запускать проект в k8s локально;
- готовность использовать тот же chart в локальной automation flow;
- понимание rollout / probes / config / ingress в реальной Kubernetes-модели.

## Как это связано с локальной automation flow

Именно этот этап должен подготовить базу для воспроизводимого локального deploy flow.

Целевой локальный pipeline после перехода на Helm должен быть примерно таким:
- lint
- test
- build image
- deploy через `helm upgrade --install`
- smoke checks

То есть **Helm должен быть главным локальным deploy-механизмом**, а не побочным инструментом.

## Что важно не делать

На этом этапе важно не усложнять систему лишними инструментами.

Не нужно:
- начинать с raw YAML как основного способа сопровождения;
- строить процесс вокруг Skaffold как обязательной основы;
- превращать локальную разработку в постоянную борьбу с Kubernetes.

Главная цель этого этапа — **перейти к локальной production-like deployment model**, а не
сделать локальную разработку максимально сложной.

# Этап 3. Дополнительно: Minikube как sandbox для Kubernetes-фич

## Зачем нужен Minikube в этом плане

Minikube не должен быть основным инструментом разработки проекта.

Его стоит рассматривать как **дополнительную песочницу** для изучения Kubernetes-возможностей:
- ingress addons;
- dashboard;
- storage classes;
- metrics-server;
- сетевые и кластерные фичи;
- ручные эксперименты с k8s-объектами.

## Почему Minikube не выбран как основной путь

Потому что для основной разработки и локальной automation flow он менее практичен, чем `kind`:
- тяжелее;
- обычно медленнее;
- хуже подходит как базовый вариант для repeatable local automation-процессов;
- в данном проекте не дает достаточного преимущества, чтобы делать его основой.

## Когда Minikube может быть полезен

Minikube полезен, если хочется отдельно:
- поизучать Kubernetes “руками”;
- попробовать разные addons;
- посмотреть более “кластерный” UX;
- поэкспериментировать с настройками, которые не хочется тащить в основной workflow проекта.

То есть это **учебная и исследовательская площадка**, а не основной контур.

## Как зафиксировать его роль

Нужно явно зафиксировать:
- Minikube **не обязателен** для проекта;
- Minikube **не является основным dev-контуром**;
- Minikube можно использовать только как дополнительный sandbox для исследования k8s-фич.

---

# Итоговое решение

Для проекта фиксируется такая стратегия:

## 1. Старт
Использовать **Docker Compose** как основной способ локального запуска на раннем этапе.

Назначение:
- быстрое развитие продукта;
- удобная отладка;
- минимальная инфраструктурная сложность.

## 2. Потом
Перейти на **kind + Helm** как основной локальный Kubernetes- и deployment-стек.

Назначение:
- запуск проекта в локальном Kubernetes;
- подготовка к production-like деплою;
- единая deploy-модель для локальной среды и automation.

## 3. Дополнительно
Использовать **Minikube** только как sandbox для изучения Kubernetes-фич и экспериментов.

Назначение:
- обучение;
- исследование ingress/addons/storage и других возможностей k8s;
- отдельные технические эксперименты.

---

# Короткая формулировка для фиксации в проекте

Инфраструктурная эволюция проекта должна идти по следующему пути:

- на старте использовать Docker Compose для локальной разработки и запуска зависимостей;
- после стабилизации core-функциональности перейти на локальный Kubernetes через kind;
- использовать Helm как основной способ описания и деплоя приложения;
- строить локальный deploy flow вокруг Helm-based deployment;
- Minikube рассматривать только как дополнительную песочницу для изучения Kubernetes-возможностей, но не как основной рабочий контур.

---

# Что Codex должен зафиксировать

Нужно зафиксировать следующие архитектурные решения:

1. **Ранний этап разработки** (E01 — E08)
   - основной локальный runtime: Docker Compose

2. **Следующий этап инфраструктурной зрелости** (E09, E12)
   - локальный Kubernetes: kind
   - deployment packaging: Helm

3. **Целевая модель локальной automation** (E09)
   - build image
   - deploy через Helm

4. **Роль Minikube**
   - необязательный sandbox для k8s-экспериментов
   - не основной инструмент разработки и не основной путь локального deploy

5. **Принцип эволюции**
   - сначала простота и скорость разработки
   - потом reproducible Kubernetes deployment
   - затем расширение экспериментов при необходимости
