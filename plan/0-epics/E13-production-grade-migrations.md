# E13 - Production Grade Migrations

Status: active

## Summary

Upgrade the project's migration setup from a developer convenience (`make migrate-up`) to a
production-shaped operational pattern. The migration tool stays the same (`golang-migrate`), but
the surrounding rules, automation, and safety nets get added.

## Goal

Make migrations safe to run against a production-like environment by enforcing forward-only
deploys, schema drift detection, expand/contract guidelines, lock/timeout discipline, and a
documented dirty-state recovery runbook. The bar is "Level 1" from the senior-golang-study
migration operations doc — enough scaffolding to learn real production patterns without pulling
in a heavier tool.

## Scope

- forward-only-in-production rule, documented and reflected in Makefile labelling
- `schema.sql` dump kept in repo as schema source of truth, with drift check
- expand/contract guidelines for destructive changes (drop column, rename, type change)
- mandatory `lock_timeout` and `statement_timeout` in every migration
- `CREATE INDEX CONCURRENTLY` rule for indexes on growing tables
- dirty-state recovery runbook
- schema-change PR template / checklist
- excludes switching to Atlas or any other tool (kept as Level 3 follow-up)
- excludes Kubernetes init containers, Helm hooks, or real CI/CD pipeline (kept as Level 2
  follow-up; this project has no k8s yet)
- excludes lint integration (Atlas / squawk) — kept as Level 2/3 follow-up

## Key Decisions

- stay on `golang-migrate`; do not introduce a second tool in this epic
- `down` migrations remain useful in development and tests, but are explicitly forbidden against
  any deployed environment
- `db/schema.sql` is regenerated by a Make target after each migration and committed alongside
  the migration files
- drift detection runs as a local Make target now; CI integration is deferred until E09
  (delivery-and-local-automation) wires a real CI pipeline
- every new migration must use `lock_timeout = 5s` and `statement_timeout = 60s`
- index creation on `links` (and any future high-traffic table) must use `CONCURRENTLY`
- the schema-change checklist lives in `docs/migrations.md` (not in a separate file) so the
  operational doc stays the single source
