# E13-002 - Add Schema Dump And Drift Check

Status: backlog

Epic: E13 - Production Grade Migrations

## Summary

Introduce `db/schema.sql` as the committed source of truth for the current PostgreSQL schema,
plus a Make target that regenerates it from `pg_dump` and a drift check that fails if the
committed file differs from the dump produced after applying all migrations.

## Scope

- new directory `db/` with `schema.sql` containing the full schema dump after all current
  migrations
- new Make targets: `schema-dump`, `schema-check`
- documentation update in `docs/migrations.md` describing when to regenerate the dump
- excludes any CI integration (will be wired in E09)
- excludes data dumps; only `--schema-only`

## Acceptance Criteria

- `db/schema.sql` exists, is generated by `pg_dump --schema-only --no-owner --no-privileges`,
  and reflects the schema after applying all migrations under `migrations/postgres/`
- `make schema-dump` regenerates `db/schema.sql` from a database that has all migrations applied
- `make schema-check` runs migrations against an ephemeral schema (or compares against the live
  one), produces a fresh dump, and exits non-zero if it differs from `db/schema.sql`
- the dump is deterministic across runs (no random comments, timestamps, or owner lines)
- `docs/migrations.md` documents the workflow: "after writing a migration, run `make migrate-up`
  then `make schema-dump`, commit both"
- the existing `links` table appears in `db/schema.sql` correctly

## Assumptions

- `pg_dump` is available locally (it ships with Postgres client tools)
- the docker-compose `postgres` service can be used as the dump source
- a single connection string with the dev DSN is enough; no need for a separate dump-only DB
- `--no-owner --no-privileges` is enough to make the dump deterministic; if not, additional
  filtering (sed) may be needed

## Implementation Notes

- prefer running `pg_dump` against the docker-compose `postgres` service to avoid requiring a
  local pg client
- target sketch:

  ```makefile
  ## schema-dump: regenerate db/schema.sql from current PostgreSQL state
  schema-dump:
  	docker compose -f $(COMPOSE_FILE) exec -T postgres \
  		pg_dump --schema-only --no-owner --no-privileges -U shortener shortener \
  		> db/schema.sql

  ## schema-check: fail if db/schema.sql is out of sync with applied migrations
  schema-check:
  	@tmp=$$(mktemp) && \
  	docker compose -f $(COMPOSE_FILE) exec -T postgres \
  		pg_dump --schema-only --no-owner --no-privileges -U shortener shortener > $$tmp && \
  	diff -u db/schema.sql $$tmp || \
  	(echo "schema drift detected — run make schema-dump and commit db/schema.sql" && exit 1)
  ```

- if dump output is not deterministic, post-process with `grep -v` to strip volatile lines
  (e.g. SET statements, comments)
- add `db/` to the project root, not under `migrations/`, to keep migration files vs schema
  snapshot conceptually separate

- inspect `db/schema.sql` for any non-deterministic lines
